# 07 · VF 间隔离与带宽切分

# 07 · 大流量下 VF 之间会互相影响吗？带宽被切分了吗？

## 1. 直接结论

> **默认：没有切分。所有 VF 竞争共享物理端口的带宽。**
> **但：可以显式配置限速（主要是 TX 方向）。**
> **RX 方向：大多数网卡无法硬隔离。**

一句话：

> **所有 VF 的带宽之和 ≤ min(物理端口速率, PCIe 链路速率)**

---

## 2. 共享点在哪里

```
                     物理端口 (100G)
                          │
                    ┌─────▼─────┐
                    │  MAC/PCS  │
                    └─────┬─────┘
                          │
                    ┌─────▼─────┐
                    │ 硬件包分类器 │  ← 硬件查表分流（MAC/VLAN）
                    └─────┬─────┘
          ┌───────┬───────┼───────┬───────┐
          ▼       ▼       ▼       ▼       ▼
        [VF0 Q] [VF1 Q] [VF2 Q] [VF3 Q] [PF Q]
          └───────┴───────┴───────┴───────┘
                        │
              ┌─────────▼─────────┐
              │  ⚠️ 共享：片上包缓冲区 │  ← 竞争点 ①
              └─────────┬─────────┘
                        │
              ┌─────────▼─────────┐
              │  ⚠️ 共享：PCIe 上行链路 │  ← 竞争点 ②（硬上限）
              └─────────┬─────────┘
                        │
              ┌─────────▼─────────┐
              │  ⚠️ 共享：内存带宽/LLC │  ← 竞争点 ③（隐藏瓶颈）
              └─────────────────────┘
```

### 资源归属表

| 层次 | 独立性 | 说明 |
| --- | --- | --- |
| 收发队列 / MSI-X 向量 | ✅ **独立** | 每 VF 独有的硬件资源 |
| DMA 地址空间 | ✅ **独立** | IOMMU 按 BDF 隔离翻译 |
| NIC 片上包缓冲区 | ❌ **共享** | 突发流量的 noisy neighbor 来源 |
| PCIe 上行链路 | ❌ **共享（硬上限）** | 所有 VF 总带宽天花板 |
| 内存带宽 / LLC | ❌ **共享** | 小包高频场景的隐藏瓶颈 |

---

## 3. 具体的相互影响场景

### 3.1 带宽竞争（最直接）

```bash
# 100G 网卡，4 个 VF
VF0 跑 40Gbps
VF1 跑 30Gbps
VF2 跑 20Gbps
VF3 跑 20Gbps
─────────────────
总计 110Gbps > 100Gbps  → 全部丢包 / 降速
```

**没限速 = 谁先发谁占便宜**（取决于硬件调度策略：通常轮询或优先级）。

### 3.2 缓冲区竞争（隐蔽杀手）

NIC 片上 buffer 有限（几 MB 到几十 MB）。

```
VF0 突发 100Gbps（应用消费慢，队列积压）
  → 吃掉大部分共享 buffer
  → VF1/2/3 即使只跑 5Gbps 也开始丢包
```

这就是 **Head-of-Line Blocking** / **noisy neighbor**。

**典型表现**：某个 Pod 疯狂发包时，其他 Pod 的 P99 时延突然飙升。

### 3.3 中断 / CPU 竞争

```
VF0 队列中断 → CPU 0-3
VF1 队列中断 → CPU 0-3   ← 冲突！
VF2 队列中断 → CPU 0-3
```

大量小包 → 高中断频率 → 软中断占用 CPU → 应用得不到调度。

**典型表现**：`si`（软中断）使用率飙高，所有 VF 的时延一起上升。

### 3.4 PCIe 事务开销

每个 VF 的队列有 doorbell 寄存器，应用发包后要写它通知网卡。

```
大量 VF × 高频写 doorbell = PCIe TLP 开销
```

在**多 VF + 小包**场景下尤其明显。

## 4. 总带宽到底是多少

**不是 N 等分**，而是取决于两个瓶颈中较小的那个：

| 网卡 | 物理端口 | PCIe 链路 | 实际上限 |
| --- | --- | --- | --- |
| Intel E810 | 100G | PCIe 4.0 x16（≈200G） | **100G**（端口限制） |
| Intel X710 | 10G | PCIe 3.0 x8（≈64G） | **10G**（端口限制） |
| Mellanox CX-6 | 100G | PCIe 4.0 x16 | **100G** |
| ⚠️ 100G 网卡插 PCIe 3.0 x8 | 100G | ≈64G | **64G（PCIe 限制！）** |

> **坑**：把 100G 网卡插在低带宽插槽，实际只能跑 64G，而且**所有 VF 共享这 64G**。

## 5. 可用的隔离手段

### 5.1 TX 限速（最常用、支持最好）

```bash
# 限制 VF 0 发送速率 25Gbps（单位 Mbps）
ip link set ens1f0 vf 0 max_tx_rate 25000

# 保底带宽（部分网卡支持）
ip link set ens1f0 vf 0 min_tx_rate 10000

# 查看
ip link show ens1f0
```

对应本插件配置的 `max_tx_rate` / `min_tx_rate` 字段。

### 5.2 DCB / ETS（数据中心桥接）

如果网卡支持 DCB：

```bash
# 配置优先级 → 带宽映射（2 个优先级各占 50%）
dcbtool sc ens1f0 ets-up2tc 0:0 1:1
dcbtool sc ens1f0 ets-cfg 0:50 1:50
```

需要交换机侧配合（DCBX 协商）。

### 5.3 队列与中断隔离

```bash
# 创建 VF 时指定队列数
echo 4 > /sys/class/net/ens1f0/device/sriov_numvfs

# 中断绑定到不同 CPU
echo 0f > /proc/irq/<irq>/smp_affinity
```

### 5.4 各厂商能力对比

| 厂商 | TX 限速 | RX 限速 | 细粒度 QoS |
| --- | --- | --- | --- |
| **Intel（ice / i40e）** | ✅ | ❌ 基本不支持 | ⚠️ DCB/ETS 有限 |
| **NVIDIA / Mellanox（mlx5）** | ✅ | ⚠️ 部分支持 | ✅ 很好（`mlx_qos`） |
| **Broadcom（bnxt）** | ✅ | ⚠️ 部分 | ✅ 较好 |

## 6. 实操建议

### 6.1 显式配置限速

```json
{
  "type": "sriov",
  "deviceID": "0000:03:02.1",
  "min_tx_rate": 5000,
  "max_tx_rate": 25000,
  "ipam": { "type": "whereabouts", "range": "192.168.100.0/24" }
}
```

### 6.2 监控 per-VF 统计

```bash
# 每个 VF 的收发包 / 字节统计
ethtool -S ens1f0 | grep -E "vf[0-9]+_(rx|tx)_(packets|bytes)"

# 或
ip -s link show ens1f0 | grep -A3 "vf 0"
```

### 6.3 NUMA 与绑核

```bash
# 网卡在哪个 NUMA 节点
cat /sys/class/net/ens1f0/device/numa_node

# 用 Guaranteed QoS + CPU Manager 把 Pod 绑到同节点 CPU
```

### 6.4 大流量场景架构建议

| 需求 | 方案 |
| --- | --- |
| 需要严格带宽保证 | TX 限速 + 交换机侧 QoS |
| 避免突发互相影响 | 网卡 buffer 管理 / 流控（PFC） |
| 极致性能且要隔离 | **考虑多张物理网卡**，而非多 VF |
| RDMA 场景 | **必须 SR-IOV**，无替代 |

---

## 7. 一句话回答

> **VF 之间会相互影响，影响程度取决于共享层的瓶颈在哪：**
>
> - **PCIe 上行带宽** → 硬上限，所有 VF 共享，饱和则一起降速
> - **片上包缓冲区** → 突发流量的 noisy neighbor 效应，表现为时延毛刺
> - **CPU / 内存带宽** → 小包高频场景的隐藏瓶颈
>
> **SR-IOV 规范本身不定义带宽切分**，需要时通过 `max_tx_rate` 显式限速，或借助 DCB/ETS 做优先级调度。
