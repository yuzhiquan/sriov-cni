# 06 · SR-IOV vs macvlan vs ipvlan

## 1. 核心区别一句话

> **macvlan / ipvlan 是「一张网卡当多张用」——软件虚拟出来的，收发包仍要过宿主机内核。**
> **SR-IOV 是「一张网卡真的裂成多张」——PCIe 硬件分出来的，收发包绕过宿主机内核。**

---

## 2. 数据面路径对比

```
   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │  VF0   │ │  VF1   │ │  VF2   │ │  VF3   │      各 VF 独立的部分：
   │ 队列 + │ │ 队列 + │ │ 队列 + │ │ 队列 + │      · 独立 PCIe BDF
   │ MSI-X  │ │ MSI-X  │ │ MSI-X  │ │ MSI-X  │      · 独立收发队列 / MSI-X
   └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘      · 独立 DMA 地址空间
       │        │        │        │                    · IOMMU 硬件隔离
       └────────┴────┬───┴────────┘
                     ▼
        ┌────────────────────────────┐
        │  ⚠️ 共享：NIC 片上包缓冲区      │  ← 竞争点 ①
        │     （所有 VF 共用同一块）      │
        └─────────────┬──────────────┘
                      ▼
        ┌────────────────────────────┐
        │  ⚠️ 共享：PCIe 上行链路        │  ← 竞争点 ②（硬上限）
        │  例：PCIe 4.0 x16 ≈ 200Gbps │
        └─────────────┬──────────────┘
                      ▼
        ┌────────────────────────────┐
        │  ⚠️ 共享：内存带宽 / LLC      │  ← 竞争点 ③（隐藏瓶颈）
        └─────────────┬──────────────┘
                      ▼
                 主机 / 应用内存
```

### 三个层次的资源归属

| 层次 | 是否独立 | 说明 |
| --- | --- | --- |
| **收发队列 / MSI-X 向量** | ✅ 独立 | 每个 VF 有自己的队列和中断 |
| **DMA 地址空间** | ✅ 独立 | IOMMU 为每个 VF 做隔离翻译 |
| **NIC 片上包缓冲区** | ❌ **共享** | 所有 VF 共用 |
| **PCIe 上行带宽** | ❌ **共享（硬上限）** | 所有 VF 流量之和的上限 |
| **内存带宽 / LLC** | ❌ **共享** | 小包高频场景的隐藏瓶颈 |

## 3. 全景对比表

| 维度 | **SR-IOV VF** | **macvlan** | **ipvlan** |
| --- | --- | --- | --- |
| **实现位置** | **网卡硬件**（PCIe 层） | 内核软件驱动 | 内核软件驱动 |
| **是不是真设备** | 是（独立 PCIe Function，有 BDF/BAR/MSI-X） | 否（虚拟接口） | 否（虚拟接口） |
| **数据面过不过内核** | ❌ **绕过** | ✅ 全程经过 | ✅ 全程经过 |
| **隔离机制** | IOMMU DMA 重映射（硬件级） | 软件隔离 | 软件隔离 |
| **MAC 地址** | 每 VF 独立 MAC | **每子接口独立 MAC** | **共享主接口 MAC** |
| **需不需要混杂模式** | 不需要（硬件分类） | **通常需要** | L2 需要 / **L3 不需要** |
| **硬件依赖** | ⚠️ 必须支持 SR-IOV | 无 | 无 |
| **数量上限** | 8\~256（硬件限制） | 几乎无限制 | 几乎无限制 |
| **热迁移** | ❌ 差（绑定硬件） | ✅ 好 | ✅ 好 |
| **宿主机抓包** | ❌ **抓不到** | ✅ 能抓 | ✅ 能抓 |
| **DPDK / RDMA** | ✅ 支持 | ❌ 不支持 | ❌ 不支持 |
| **相对吞吐** | ★★★★★ | ★★★☆ | ★★★★ |
| **相对时延** | 最低 | 中 | 中低 |

## 4. 三个关键差异点详解

### 4.1 MAC 地址处理 —— 云环境的生死线

这是三者**最实际**的差异，也是 ipvlan 存在的最大理由。

```
macvlan：
  主接口 ens1f0   MAC: aa:aa:aa:aa:aa:aa
    ├─ macvlan0   MAC: 02:11:22:33:44:01   ← 独立 MAC
    ├─ macvlan1   MAC: 02:11:22:33:44:02   ← 独立 MAC
    └─ macvlan2   MAC: 02:11:22:33:44:03   ← 独立 MAC

  交换机端口需要学习 4 个 MAC
    ↓
  ⚠️ 公有云 / 虚拟交换机的安全策略（防 MAC 劫持）会直接丢包！


ipvlan L2 模式：
  主接口 ens1f0   MAC: aa:aa:aa:aa:aa:aa  ← 所有子接口共用
    ├─ ipvlan0   MAC: aa:aa:aa:aa:aa:aa
    ├─ ipvlan1   MAC: aa:aa:aa:aa:aa:aa
    └─ ipvlan2   MAC: aa:aa:aa:aa:aa

  交换机只看到 1 个 MAC → ✅ 云环境友好
```

**结论**：

| 环境 | 选择 |
| --- | --- |
| 裸金属 / 自有网络 | macvlan 没问题 |
| **公有云 / VMware / 虚拟交换机** | **必须 ipvlan**（macvlan 大概率不通） |

### 4.2 数据面性能开销在哪

**macvlan / ipvlan 的开销**：

```
收包：
  NIC DMA → host 内存（host 驱动申请的 buffer）
    → 内核软件查表，决定交给哪个子接口
    → 走一遍 host 协议栈
    → 拷贝到应用内存

  ⚠️ 多了一次软件转发 + 一次拷贝

SR-IOV：
  NIC DMA → 应用内存（队列是应用 mmap 的）
    → 应用直接看到包

  ✅ 零拷贝，无软件转发
```

**结论**：

- **大包吞吐**：三者差距不大（都能跑满线速）
- **小包 PPS / 时延**：SR-IOV 优势明显（软件转发是瓶颈）

### 4.3 与父接口通信（经典坑）

三者的**共同限制**：子接口 ↔ 父接口之间**默认不能直接通信**。

原因是流量设计上"直接从 NIC 出去"，不经过 host 协议栈，所以 host 自己收不到。

```
Pod (macvlan0) ──✗──> host ens1f0
```

**解决方案**：再建一个 macvlan/ipvlan 接口给 host 用，并加路由。

```bash
# host 侧
ip link add host-mv link ens1f0 type macvlan mode bridge
ip addr add 192.168.1.2/24 dev host-mv
ip link set host-mv up
```

## 5. macvlan vs ipvlan 单独对比

|   | **macvlan** | **ipvlan** |
| --- | --- | --- |
| **MAC** | 每个子接口一个 MAC | 共享主接口一个 MAC |
| **区分流量靠** | 目的 MAC | IP 地址 |
| **交换机 MAC 表压力** | 大（N 个 MAC） | 小（1 个 MAC） |
| **混杂模式** | 通常需要 | L2 需要，**L3 不需要** |
| **DHCP** | 正常（每 MAC 一个） | ⚠️ L2 模式有问题（同 MAC 多 IP，DHCP client ID 冲突） |
| **无线网卡** | ❌ 基本不可用 | ✅ L3 模式可用 |
| **桥接 / 虚拟化环境** | ⚠️ 常被拦 | ✅ 友好 |

### ipvlan 的两种模式

- **L2 模式**：子接口在同一广播域，行为接近 macvlan，但共享 MAC
- **L3 模式**：纯三层，子接口间流量走路由，**不需要广播/ARP**，性能更好

> 简单记：**macvlan = 多个 MAC；ipvlan = 一个 MAC 多个 IP**

## 6. 选型决策树

```
需要 RDMA / DPDK / 极致性能？
  ├─ 是 → SR-IOV（唯一选择）
  └─ 否 ↓

运行在公有云 / 虚拟交换机上？
  ├─ 是 → ipvlan（L3 模式优先）
  └─ 否 ↓

需要热迁移 / 弹性伸缩？
  ├─ 是 → macvlan / ipvlan
  └─ 否 ↓

有支持 SR-IOV 的网卡，且是裸金属？
  ├─ 是 → SR-IOV
  └─ 否 → macvlan / ipvlan
```

---

## 7. 典型场景推荐

| 场景 | 首选 | 理由 |
| --- | --- | --- |
| **电信 NFV / 5G UPF** | SR-IOV + DPDK | 需要线速转发，可绑定硬件 |
| **AI 训练 / RDMA** | **SR-IOV（必须）** | RDMA 需要硬件队列 |
| **高频交易** | SR-IOV | 微秒级时延要求 |
| **裸金属 K8s，Pod 直连物理网** | macvlan | 无云限制，配置简单 |
| **公有云容器** | ipvlan L3 | MAC 限制 + 性能好 |
| **需要 NetworkPolicy** | **都不行** | 回归 Calico / Cilium |

## 8. 一个容易忽略的对比：可观测性

这是 SR-IOV 最大的"隐性成本"：

| 操作 | macvlan / ipvlan | SR-IOV |
| --- | --- | --- |
| `tcpdump -i ens1f0` 抓 Pod 流量 | ✅ 能抓 | ❌ **抓不到**（绕过内核） |
| `conntrack -L` | ✅ 有 | ❌ 无 |
| iptables 统计 | ✅ 有 | ❌ 无 |
| `ethtool -S` 硬件统计 | ✅ | ✅ |
| 交换机端口镜像 | ✅ | ✅ |

**排错提示**：SR-IOV 只能靠硬件统计 + 镜像端口排查，比 macvlan 麻烦得多。如果团队还没有配套的可观测手段，macvlan / ipvlan 往往是更稳妥的选择。
